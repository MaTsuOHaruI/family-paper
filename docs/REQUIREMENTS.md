# 1. プロジェクト概要

## 1.1 プロジェクトの目的

Family Paperは、小学生・中学生などの子どもを持つ保護者を対象とした、学校関連書類と家庭の予定を一元管理するモバイルアプリケーションである。

学校から配布されるプリント、提出書類、行事案内、給食献立、テスト関連資料などをスマートフォンで撮影・保存し、子どもごとに整理できるようにする。

また、書類に記載された学校行事や提出期限などの情報をカレンダーで管理し、重要な予定を見落とさないようにする。

将来的にはOCRとAIを利用し、書類から日付・イベント名・提出期限などを自動抽出する機能を実装する。

## 1.2 解決する課題

保護者は日常的に多くの学校関連書類を受け取る。

現在の管理方法には、次のような問題がある。

- 紙のプリントが増え、必要な書類を探すのが難しい。
- 兄弟姉妹の書類が混在する。
- 提出期限や学校行事の日程を忘れる。
- 書類を写真で保存しても、あとから見つけにくい。
- カレンダーと元の学校プリントが別々に管理されている。

Family Paperは、これらの問題を一つのアプリケーションで解決することを目指す。

## 1.3 基本コンセプト

Family Paperの中心となる機能は次の2つである。

1. Family Calendar：家族・学校関連の予定管理
2. Child-specific Document Folders：子ども別の学校書類管理

書類と予定を関連付けることで、予定の確認から元のプリントの閲覧までを一つのアプリ内で完結できるようにする。

# 2. 対象ユーザー

## 2.1 メインユーザー

- 小学生・中学生の子どもを持つ保護者
- 学校から配布される書類を管理する保護者
- 複数の子どもの予定や書類を管理する家庭
- スマートフォンで日常的に情報を管理したい保護者

## 2.2 利用単位

利用単位は個人の保護者アカウントとする。

1つのアカウントで1人以上の子どもを登録できる。

初期バージョンでは、学校や教育機関向けの管理機能は対象外とする。

## 2.3 利用シナリオ

### Scenario A：学校プリントの保存

1. 保護者がアプリを開く。
2. 書類登録画面を開く。
3. 子どもを選択する。
4. 学校プリントを撮影または画像から選択する。
5. 書類カテゴリを選択する。
6. 書類を保存する。
7. 子ども別のフォルダから保存した書類を確認する。

### Scenario B：学校行事の予定管理

1. 保護者が学校行事のプリントを登録する。
2. 書類に記載された行事情報を確認する。
3. 行事名と日付を入力または修正する。
4. カレンダーに予定を登録する。
5. カレンダーから該当する予定を開く。
6. 関連する元の学校プリントを確認する。

### Scenario C：複数の子どもの管理

1. 保護者が複数の子どもを登録する。
2. 書類登録時に対象の子どもを選択する。
3. 子どもごとに異なる書類フォルダへ保存する。
4. 選択した子どもの書類だけを表示する。

# 4. 機能要件

優先度は以下の基準で定義する。

- P0：初期リリースに必須
- P1：基本機能完成後に実装
- P2：将来の拡張機能

## 4.1 アカウント管理

### FR-001：保護者アカウント登録（P0）

保護者が個人アカウントを作成できること。

### FR-002：ログイン・ログアウト（P0）

保護者が安全にログイン・ログアウトできること。

### FR-003：ユーザー情報管理（P1）

保護者がプロフィール情報を確認・編集できること。

### FR-004：アカウント削除（P1）

保護者がアカウントと関連データの削除を要求できること。

削除時には関連する個人データと保存画像の取り扱いを明確にすること。

## 4.2 子ども管理

### FR-010：子ども登録（P0）

保護者は1人以上の子どもを登録できること。

登録項目：

- 名前またはニックネーム
- 学年
- 学校名（任意）
- 表示用カラー（任意）

### FR-011：子ども情報編集（P0）

登録した子どもの情報を変更できること。

### FR-012：子ども削除（P1）

登録した子どもを削除できること。

削除時には関連書類・予定の扱いを確認し、意図しないデータ消失を防ぐこと。

書類一覧画面で対象の子どもを切り替えられること。

選択中の子どもが明確に分かるUIにすること。

## 4.3 書類管理

### FR-020：書類登録（P0）

保護者は学校関連書類を登録できること。

登録方法：

- カメラで撮影
- 端末内の画像から選択

### FR-021：単一画像登録（P0）

1枚の画像を1つの書類として登録できること。

### FR-022：複数画像登録（P0）

複数枚の画像を1つの書類として登録できること。

複数画像は1つの書類に属するページとして管理する。

### FR-023：元画像の保存（P0）

登録された画像はオリジナルデータを保存すること。

OCR結果や加工画像で元画像を置き換えてはならない。

OCR失敗時にも元画像が残ること。

### FR-024：書類情報登録（P0）

書類には以下の情報を設定できること。

- 書類タイトル
- 対象の子ども
- カテゴリ
- 登録日
- メモ
- 画像ページ

### FR-025：書類カテゴリ（P0）

初期カテゴリは以下とする。

1. 学校行事
2. 提出書類
3. 給食・献立
4. テスト・成績
5. 部活動
6. その他

将来的にカテゴリを追加できる構造にすること。

### FR-026：書類一覧表示（P0）

選択中の子どもに属する書類のみを一覧表示できること。

### FR-027：書類詳細表示（P0）

書類を選択すると、登録情報と保存画像を確認できること。

複数画像の場合はページを切り替えて閲覧できること。

### FR-028：書類編集（P0）

書類タイトル、カテゴリ、メモなどを変更できること。

### FR-029：書類削除（P0）

保護者が書類を削除できること。

削除前に確認画面を表示すること。

関連するカレンダー予定を自動的に削除してはならない。

## 4.4 OCR・AI情報抽出

初期リリースではOCRとAI解析は段階的に実装する。

### FR-030：画像OCR（P1）

登録した画像から文字情報を抽出できること。

### FR-031：書類情報解析（P1）

OCR結果から以下の情報を抽出できること。

- 書類タイトル
- 学校名
- 行事名
- 行事日
- 提出期限
- 配布日
- 対象学年
- 必要な持ち物
- メモ

### FR-032：日付の分類（P1）

日付を次の3種類に分類すること。

- Event Date：行事が実施される日
- Submission Deadline：提出期限
- Distribution Date：プリントの配布日

これらを混同してはならない。

### FR-033：抽出結果の確認（P1）

AIが抽出した情報は、保護者が確認・編集できること。

確認前に予定を自動登録してはならない。

### FR-034：抽出失敗時の処理（P1）

OCRやAI解析が失敗しても、登録済みの元画像は保持すること。

エラー内容を表示し、手動入力で続行できること。

### FR-035：AI解析結果の保存（P1）

抽出結果、処理状態、確認状態を保存できること。

### FR-036：AI処理状態表示（P1）

以下の状態を管理すること。

- pending
- processing
- completed
- failed
- reviewed

# 7. セキュリティ要件

## SEC-001：ユーザー間のデータ分離

保護者は自分のアカウントに属するデータのみ閲覧・編集できること。

## SEC-002：Row Level Security

Supabaseの全ユーザーデータテーブルに適切なRLSポリシーを設定すること。

`parent_id = auth.uid()` を基本とし、子ども・書類・予定の関連データも所有者を検証すること。

単にクライアント側で表示を制限するだけでは不十分である。

## SEC-003：Storageのアクセス制御

学校書類画像はprivate bucketに保存すること。

認証済みユーザーが自分のデータに属する画像だけを取得できるようにすること。

Storageのポリシーでも所有者を検証すること。

## SEC-004：秘密情報の保護

- service_role keyをクライアントに含めない。
- API SecretをGitHubに登録しない。
- `.env` をGit管理対象外にする。
- 公開用キーだけをクライアントに設定する。
- AIサービスの秘密鍵は将来サーバー側で管理する。

## SEC-005：データ削除

ユーザーが書類やアカウントを削除した場合、データベースとStorageの整合性を保つこと。

削除処理が途中で失敗した場合に、孤立ファイルが残らないようにすること。

# 8. 非機能要件

## NFR-001：操作性

- 初めて利用する保護者でも理解できるUIにする。
- 主要操作は少ないステップで完了できるようにする。
- 重要な情報を視覚的に区別する。

## NFR-002：パフォーマンス

- 画面表示時に不要な大量データを読み込まない。
- 書類一覧ではページネーションを考慮する。
- 画像は必要に応じてサムネイルを利用する。
- 元画像は別途安全に保持する。

## NFR-003：信頼性

- OCR失敗時にも元画像を保持する。
- ネットワークエラー時に適切なメッセージを表示する。
- 保存処理中の二重登録を防ぐ。
- 途中で失敗した処理から復旧できるようにする。

## NFR-004：保守性

- UIとデータ処理を分離する。
- TypeScriptの型を適切に定義する。
- 共通コンポーネントを再利用する。
- 将来のOCR・AIプロバイダー変更に対応する。

## NFR-005：プラットフォーム対応

iOSとAndroidの両方で基本機能が動作すること。

# 9. MVP（最小実用製品）の定義

最初のリリースでは、以下をMVPの完成条件とする。

1. 保護者がアカウントを作成・ログインできる。
2. 子どもを1人以上登録できる。
3. 子どもごとに書類を整理できる。
4. 単一画像と複数画像を登録できる。
5. 元画像をSupabase Storageに保存できる。
6. 書類の詳細を閲覧・編集・削除できる。
7. カレンダーで予定を確認できる。
8. 予定を手動登録・編集・削除できる。
9. 書類と予定を関連付けられる。
10. 他のユーザーのデータにアクセスできない。

OCR・AIによる自動抽出はMVPの基本機能が安定した後に追加する。

# 11. 受け入れテスト

以下の条件を満たすことを確認する。

## AT-001：複数の子ども登録

1つのアカウントで複数の子どもを登録できる。

## AT-002：子ども別の書類表示

子どもAを選択したとき、子どもBの書類が混ざらない。

## AT-003：単一画像登録

1枚の画像を登録し、あとから閲覧できる。

複数枚の画像を1つの書類として登録でき、ページ順を保持する。

OCR処理や画像表示用の加工によって元画像が失われない。

## AT-006：予定登録

カレンダーに予定を登録し、あとから編集できる。

## AT-007：書類・予定連携

予定から関連する元書類を開ける。

書類を削除しても、関連予定は自動削除されない。

## AT-009：OCR失敗

OCR処理に失敗しても元画像が保持され、手動入力を続行できる。

## AT-010：ユーザー間のデータ分離

別の保護者アカウントから他のユーザーのデータや画像にアクセスできない。

# 13. Claude Codeへの開発ルール

Claude Codeは以下のルールに従って開発すること。

1. 実装前に必ず関連する要件IDを確認する。
2. 一度に大きな機能を実装せず、小さなタスクに分割する。
3. 実装した機能と未実装機能を明確に区別する。
4. 要件にない機能を勝手に追加しない。
5. 重要な仕様変更は実装前に確認する。
6. TypeScriptの型安全性を維持する。
7. 変更後は関連するテストと型チェックを実行する。
8. エラーを無視して完了扱いにしない。
9. データベースの変更はSupabase migrationで管理する。
10. セキュリティに関係する変更は必ず説明する。
11. サンプルデータと本番データを明確に区別する。
12. 元画像の保存を最優先し、OCR・AI処理で上書きしない。

各タスク完了時には以下を報告する。

- 実装した要件ID
- 変更したファイル
- 実装内容
- テスト結果
- 未解決の問題
- 次に推奨するタスク
